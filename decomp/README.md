# default.xbe decompilation

Raw C decompilation of every function in the game's `.text` section, taken from the analyzed Ghidra project. This is the starting point for a full decompilation; it does **not** compile or run yet.

## Status

7,981 functions in `.text`, all decompiled (0 failures). They're split by origin using `analysis/modules.tsv`:

| module | functions | code bytes | named | what it is | where |
|---|---|---|---|---|---|
| **game** | 6,318 | 1,086,346 | 40 | the game itself | `src/` |
| **engine_core** | 274 | 54,973 | 3 | developer's core library ("elem"/"bent": memory debug, crash log, disk, strings) | `src/engine_core/` |
| **static_init** | 181 | 4,432 | 0 | compiler-generated constructors for game globals | `src/static_init/` |
| lua | 513 | 75,809 | 138 | Lua 5.0 (Tecgraf/PUC-Rio), statically linked | `lib/lua/` |
| crt | 438 | 52,337 | 194 | MSVC 7.1 C runtime + C++ exception handling | `lib/crt/` |
| xapi | 257 | 40,781 | 145 | Xbox XAPI (files, threads, save games, memory) | `lib/xapi/` |

The **6,773 functions in `src/`** (about 1.15 MB of machine code) are what actually needs decompiling. The **1,208 in `lib/`** are reference only: on Windows they're replaced by stock Lua 5.0, the platform's C runtime, and Win32 equivalents. Direct3D 8, DirectSound and XGraphics are in their own XBE sections and are never in `.text`.

`functions.tsv` tracks every function: address, name, size, module, file, where the name came from, and status (`raw` for game code, `library` for lib code).

## Layout

```
  ghidra_types.h          typedefs and CONCAT/SUB/ZEXT macros that Ghidra's output uses; includes dra2_formats.h

```

### How the libraries were identified

- **Lua 5.0:**
  - The version string is in the binary (`$Lua: Lua 5.0 Copyright (C) 1994-2003 Tecgraf, PUC-Rio $`). The library tables include `getmetatable`/`setfenv`, which exist only from 5.0, so it isn't 4.0.
  - The **range was set from the call graph**: from `0x1b2790` on, functions call only Lua and the C runtime, while the functions just before it call game code.
  - **138 functions are named:**
    - 110 from the nine `luaL_reg` tables in `.rdata` (`luaB_print`, `lua_math_sin`, `lua_str_format`, `lua_io_open`, …), generated by `tools/lua_names.py`.
    - 28 core functions from error messages unique to one function in the Lua 5.0 source (`luaV_execute`, `luaD_call`, `luaG_typeerror`, `luaL_loadbuffer`, …).
- **CRT and XAPI:** named by Ghidra's Function ID and Xbox symbol database analyzers. The ranges are where those names cluster, with the boundary functions checked by their callers.
- **No other third-party code:** I searched for zlib, Bink, Miles and other middleware strings and found nothing.

Address order roughly follows the original link order. MSVC places each object file's functions together, so neighbouring functions usually come from the same original `.cpp`.

## Compile check

Compiler: **LLVM/clang 23.1.4**, portable, in `C:\Users\Veo\Tools\clang+llvm-23.1.4-x86_64-pc-windows-msvc`. The download's SHA-256 matched the release's in-toto attestation.

Run it in two steps:

```

python -I tools/compile_check.py decomp C:\Users\Veo\Tools\clang+llvm-23.1.4-x86_64-pc-windows-msvc\bin\clang.exe
```

What it does:
- **Header:** `ExportHeader.java` writes every program type (format structs, 565 class structs and vtables, analyzer types) plus 11,096 prototypes. It compiles with **0 errors**, and the format struct sizes are checked with `_Static_assert`.
- **Prototypes:** for functions defined in `src/`, these are taken from their exported definitions (`build/protos.h`), so declaration and definition always agree.
- **Globals:** the labels the code uses (`DAT_`, `PTR_`, `LAB_`, `s_`, `stack0x…`) are declared in `build/globals.h`. `&X_vftable` becomes `&X_vftable_data`, because in C the name can't be both the vtable's struct type and its data.
- **Results:** every error is attributed to the function it's in. The result goes to `build/compile_report.tsv`, and the tracker's `status` column becomes `compiles` or `errors`.

**Result: 12,062 of 12,086 game/engine functions (99.8%) compile cleanly**, with 36 errors left in 24 functions. That includes the 3,833 data-referenced functions and the 180 callback functions described below. Every error, with its source line, is in `build/compile_errors.txt`.

The build step's translations matter for anyone reading `build/pp/` (the raw `src/` stays as Ghidra wrote it):
- **`code` returns a value.** Ghidra's `code` (an indirect-call target with an unknown signature) has an undefined return type, and the decompiled code assigns its result to ints, chars and pointers. So it's declared `int code()`: unspecified parameters, register-sized result. This removed about 1,200 errors.
  For calls whose result is used as a float, the x87 return value isn't modelled; that's a semantic gap, not a compile error.
- **Float↔pointer casts.** Ghidra's casts are bit reinterpretations, typically one stack slot reused for a pointer and a float. Using each function's own declarations, the build step rewrites them:
  - `(float)ptrVar` → `(*(float *)&ptrVar)`;
  - `(T *)floatVar` → `(*(T **)&floatVar)`.
  Casts on elements and members (`(float)p[2]`, `(float)p->f`) aren't touched by this textual rule. A second pass handles them from clang's own error positions:
  - lvalues (elements, members) become `(*(T *)&(x))`;
  - computed values become `(*(T *)&(float){expr})`.

  266 casts were rewritten this way. A `double` value squeezed through `(float){…}` loses precision, which is acceptable for a type check but not for running the code.
- **Ghidra pseudo-names** are declared in `globals.h`:
  - absolute-address variables typed from their Hungarian prefix (`piRam000001f8` → `int *`);
  - the `luakey_*` string labels (`char[]`);
  - `register0x…`, `_param_N`, `_local_N` (split or register storage);
  - namespaced data such as `XAPILIB__g_DeviceType_Gamepad`.
- **Switches** on float or pointer values (a decompiler artefact, since jump tables are integer code) become `switch((int)(…))`, with `case N.0:` / `case (T *)N:` turned into `case N:`.
  One of the three affected functions, `FUN_00094b40`, is there because `FixFloatLocals.java` wrongly made its switch index `puVar2` a `float` (a reused stack slot). That variable should be set back by hand in Ghidra.
- **Duplicate names.** Ghidra allows two methods with the same name in one class (e.g. two `ctor`s); C doesn't. The second and later definitions get their address as a suffix (314 renamed), and calls keep pointing at the first. The real fix is distinct names in Ghidra.
- **Partial variables.** Ghidra's `x._2_1_` means "1 byte at offset 2 of `x`". It isn't C, so it becomes `(*(unsigned char *)((char *)&x + 2))`, which has the same semantics.
- **Untyped globals.** A `DAT_`/`PTR_` label that the code dereferences, subscripts or uses with `->` is declared `undefined4 *` (80 globals); every other untyped global is `undefined4`.

Together these removed almost all of the "member reference on a non-struct / indirection on a non-pointer" errors (about 1,340 → about 60). Those weren't struct-pointer typing problems after all.

**Signatures (`CommitSignatures.java`).** At first the decompiler re-inferred each function's parameters separately in every function that called it, so definitions and calls disagreed (about 6,500 errors). The script now commits a signature for every function that had none:
- **Committed:** 7,786 game/engine functions, then 3,104 library and XDK functions (Lua's C API, the CRT's `__stricmp` and `_vsnprintf`, XAPI, D3D8 …), all from the decompiler's own inference.
- **Callee-cleanup functions (`RET n`)** must take exactly *n* bytes of stack arguments, so 410 parameter lists were padded or trimmed to match and 127 functions became `__stdcall`.
- A backup of the project from before this step is in `ghidra/backup_before_signatures/`.

**Error-driven rewrites (latest round).** Each runs only where clang reports that error, then the file is recompiled (up to six passes):
- **Mismatched calls** (callee typed `void *`, wrong argument count, `void` result used) are routed through `((code *)callee)(…)`, which is what the machine code does: arguments are pushed, a register-sized value comes back. Multi-line calls are found by walking back up to three lines.
- **Integer `case` labels printed as floats** (`case 1.4013e-45:` is the integer 1 read as a float) become `case 1:`.
- **Casts** now parse their whole operand: unary prefixes, nested casts, and trailing `->field`, `[i]` and calls.
- **Pointer-typed globals used as numbers** are read as `float` or `uint` at that use.
- **Untyped labels used as structs** get byte-offset access.
- **10-byte x87 values** (`undefined1[10]` returns, locals and casts) are `float10`.
- `NAN(x)` means "is NaN"; a bare `NAN` is the NaN constant.

**What's left: 21 functions, 32 errors.** They are one-off decompiler artefacts, e.g. a subscript on a function-typed local, or `ctor` used as a bare name in an array-constructor call. They are best fixed by hand in Ghidra.
The object build (below) replaces each of their bodies with a trap, so they don't block the build.

**Class fields (`TypeClassFields.java`):**

- It ran on 1,152 of 2,605 methods; the rest never dereference `this` in a way the decompiler can follow.
- All **5,957 vtable slots** are now pointers to function types built from the slot methods' committed signatures, e.g. `GameMode_slot00_0a9620_fn`.
- A backup from before this step is in `ghidra/backup_before_fields/`.

**Floats.** x87 float values often ended up in integer- or pointer-typed variables and fields, which the compile check reports as "pointer cannot be cast to `float`". - **`FixFloatFields.java`:** a struct field becomes `float`/`double` when a load from it feeds a float operation, or a store to it comes from one, and it's never dereferenced. It retyped **170 fields** (list in `analysis/float_fields.tsv`).
- **`FixFloatLocals.java`:** does the same for locals and parameters, following values through the casts the decompiler shows as `(float)var`. It retyped **98 locals and 11 parameters** (`analysis/float_fixes.tsv`).

Float-cast errors fell from 1,141 to 362.

**Header fixes that came with it** (in `ExportHeader.java`):
- Inferred fields keep their real names (`field48_0x3c`); only one-byte `undefined` filler is renamed to the decompiler's `field_0x…`.

### Exception frames removed

On the Xbox every function with C++ cleanup builds an MSVC exception frame by hand: it links into `fs:[0]` and stores a pointer to its unwind record. The decompiled code shows that as `*unaff_FS_OFFSET = …` and `puStack_8 = &LAB_001f…`.

The build step now:
- drops the frame links;
- reads `fs:[0]` as 0;
- replaces unwind-record addresses (`0x1ee000–0x1f9da0`) with null.

This removed the 1,063 unwind-record symbols. It matters at run time too: `unaff_FS_OFFSET` would otherwise be an uninitialised pointer that gets written through.

### XAPI (`port/xapi.c`)

Every implementation keeps the name, calling convention and parameter count of the prototype the game is compiled against, so its decorated name matches the stub exactly. That was checked for all 48 symbols.
All of them are `__stdcall`, except `XPhysicalFree`, which the game's prototype declares cdecl.

- **Kernel objects, threads, timing:** passed straight to Win32 (`CreateThread`, events, mutexes, waits, `Sleep`, `QueryPerformanceCounter`, `GetLastError`).
- **Memory:** `GlobalMemoryStatus` has the same layout on both. The heap goes to the Windows process heap. `XPhysicalAlloc`/`Free` become `VirtualAlloc`/`VirtualFree`.
- **Files and paths:** the game uses Xbox drive letters.
  - `d:\` (the disc) maps to `%DRA2_DATA%`, or `<exe folder>\data` if that isn't set.
  - `u:\` (saves) and the `t:\`/`z:\` scratch drives map to `%DRA2_SAVES%\u|t|z`, or `<exe folder>\saves\…`.
- **Save games:** each save is a folder under `u:\`, named by a 48-bit hash of its display name. The display name is kept in `savename.bin` so `XFindFirstSaveGame`/`XFindNextSaveGame` can list it. `XCreateSaveGame` honours `CREATE_NEW`/`OPEN_EXISTING`/`OPEN_ALWAYS`; `XDeleteSaveGame` removes the folder.
- **Save signatures:** the Xbox signs saves with a per-console key. Here a stable 20-byte digest is enough, because the PC build only checks its own saves.
- **Gamepads:** Windows XInput (`xinput1_4.dll`, falling back to `xinput9_1_0.dll`), loaded at run time.
  - Button mapping: the Xbox analog face buttons A/B/X/Y become 0 or 255; Black comes from the right shoulder, White from the left; triggers and sticks map directly; the d-pad, Start, Back and stick-click bits are identical.
  - `XGetDevices`/`XGetDeviceChanges` report connected pads. No memory units are reported, so saves go to `u:\`.
  - Rumble: the game writes the motor speeds at `+0x42`/`+0x44` of `XINPUT_FEEDBACK` (checked at its call site).
- **Settings:** English, NTSC, 4:3. `XLaunchNewImageA` (back to the dashboard) quits.

| `_ftol`, `_CIacos`, `_CIasin`, `_CIatan2`, `_CIpow` (as `CRT_…`) | `port/crt_math.c` |
| `exception::exception()`, copy constructor, `_CxxThrowException` (as `CRT_…`) | `port/cxx_runtime.c`; a throw is reported and aborts, since the port has no exception frames |
| `CreateDirectoryA` (`0x1eb830`, really XAPI) | `port/xapi.c`, with drive-letter mapping |

Three things came up along the way:
- **x87 helpers.** MSVC passes their operands on the FPU stack (`_ftol`: `ST0` → `EDX:EAX`; `_CIpow(x, y)`: `ST1`, `ST0`). The decompiled calls had lost those arguments. The table gives them custom register storage, so every call site now shows them, e.g. `CRT_ftol((float10)dVar7)`, and they become ordinary C functions in the port.
- **Wrong calling conventions.** Six already-named CRT functions had been committed as `__stdcall` (`__stricmp`, `__strnicmp`, `__vsnprintf`, `__controlfp`, `__ceil_default`, `__floor_default`). Linked against the real cdecl CRT, that would have broken both the symbol names and the stack. They're cdecl now.
- **Module boundary.** `0x1dd3a0–0x1dd5ff` isn't CRT. It's the engine's R250 random generator and small allocator helpers, so they now go to `src/engine_core` and are compiled. The CRT starts at `_memmove` (`0x1dd600`).

All C runtime calls now resolve to the Windows CRT or to the port. The only unnamed library functions left are **43 Lua 5.0 functions**.

### Xbox kernel imports

The XBE imports **158 kernel functions** through the thunk table at the start of `.rdata` (`0x292980`, one `0x80000000 | ordinal` word each). Ghidra's loader labels every entry with its kernel name.
- **The game never calls the kernel itself.** There's no reference to any import name, no `PTR_` label or raw address in the table from `src/` (game + engine core), and no pointer into the table from data.
- 90 imports are used only inside the Xbox libraries (CRT, XAPI, D3D8, DSOUND), which the port replaces.
- 68 aren't referenced at all.

So no kernel function needs a Windows implementation. To fail loudly rather than jump to a raw ordinal, `gen_data.py` points every table entry at a generated stub. The stub calls `port_kernel_unimplemented("<name>")` (in `platform.c`), which prints the import and aborts.

### Suggested order

1. **XAPI** first. It's mostly direct Win32 calls, and it's what boot, file loading and timing need.
2. **Input** (XInput; the action ids are already decoded).
3. **Sound.**
4. **Direct3D**, the largest part.

**Linking an `.exe`** also needs the Windows SDK and the MSVC C runtime (Visual Studio Build Tools). So far only LLVM is installed, which is enough to compile but not to link against Win32/XInput/XAudio2.

## Typing

`dra2_formats.h` defines every decoded resource format as C structs: container, TOC/index, Lua chunk, sounds, textures, materials, meshes and vertices, skeleton, animation, level and scene graph.

`tools/ghidra_scripts/TypeEngine.java` imports it into the Ghidra project. It checks the struct sizes against the real data (Bone 160, SkinnedVertex 60, StaticVertex 44, ShaderLayer 120, ResTocEntry 20, MeshDescriptor 44). Then it:
- **Applies signatures** to the resource API (`Res_ValidateHeader`, `Res_Find`, `Res_FindNextOfType`, `Lua_RunScriptResource`, `luaL_loadbuffer`, `operator_new`).
- **Types results:** for each of the **114 `Res_Find` calls with a known tag**, the local variable receiving the result becomes a pointer to that tag's struct (64 locals). Where the result is passed to another function, that parameter is typed too, for up to three hops (16 parameters). A parameter is only typed when every flow agrees, and there were no conflicts.
- **Restores error-message arguments:** it writes **printf-style call-site prototypes** for `FatalErrorf` (23 calls), so the decompiler shows the real format arguments instead of dropping them.

Result: **125 game/engine functions** now use the resource structs. For example, `Res_ValidateHeader` reads `header->magic`, `header->platform` and `header->types[i]`, and `Lua_RunScriptResource` reads `chunk->length` and `chunk->text`.

Re-run `TypeEngine.java` after editing the header. It's idempotent: types are replaced, not duplicated.

## Classes

Most of the game works on the engine's own C++ objects (characters, menus, effects, the runtime scene graph), not on file data.

**No RTTI for game classes.** The only RTTI type names are standard-library exceptions in the `_STL` namespace. So the game used **STLport** as its C++ standard library. STLport is header-only template code, compiled into game functions, so it can't be split out into `lib/` the way Lua was.

Classes are therefore recovered from vtables by `tools/ghidra_scripts/RecoverClasses.java`:
1. **Vtables:** any constant stored to `[reg+0]` (`mov dword ptr [esi], vtable`) that points at a run of code pointers in `.rdata`. That finds **565 classes**; the functions that store a vtable are its constructors/destructors.
2. **Object sizes:** taken from `push N / call operator_new / … / call <ctor>`. **301 classes** have a size. When several sizes are seen, the smallest is the class's own (bigger ones come from subclasses with inlined constructors).
3. **Inheritance:** a constructor that calls another class's constructor before storing its own vtable derives from it. **277 classes** have a parent. For example, `MenuScreen` is the base of every menu screen.
4. **Methods:** each vtable slot belongs to the class that introduces it (the one whose ancestors don't share the slot).
   - That assigns **2,026 virtual methods** to a single class; 160 slots shared by unrelated classes are left alone.
   - **828 constructors/destructors** move into their class too.
   - Vtable slots also exposed about 1,000 virtual methods Ghidra's analysis had missed, so `.text` now has **9,017 functions**.

`ClassFixups.java` then sets `__thiscall` on every class function, so all **2,923 class functions get a typed `this`**. It rebuilds each class struct with its size and a typed `vftable` field, and applies names from `analysis/class_names.tsv`. For example, `DebugMenuItem::DebugMenuItem_ctor` now reads `this->vftable = &DebugMenuItem_vftable; … this->field_0x1c` (its 100-character label).

**Naming classes:** `tools/class_hints.py` lists, for each class, the strings and Lua config tables its methods use (`analysis/class_hints.tsv`). `tools/class_tree.py` prints the hierarchy with those hints, which is the quickest way to name whole families.

One earlier guess was corrected: the class first called `MatchAnnouncer` is the base of every game mode, so it's now `GameMode`. Classes are tracked by vtable address, so renaming is safe to repeat.

**Method names** come from `NameMethods.java`, which names structurally and only touches functions still called `FUN_*`:
- `deleting_dtor` (506): the scalar deleting destructor pattern, `flags & 1` then `operator delete`.
- `dtor` (393): the function the deleting destructor calls.
- `ctor` (430): the remaining vtable writers.
- `vfNN` (1,506): every other virtual method, named by vtable slot. An override has the same name as the base method it replaces, e.g. `MenuOptions::vf05` overrides `MenuScreen::vf05`, so one slot's role can be read across a whole family.

To add names: append to `class_names.tsv`, then run `ClassFixups.java <class_names.tsv> <classes.tsv>` and `NameMethods.java <classes.tsv>`, then re-export.

**Slot names.** `tools/vtable_slots.py` summarises a family's vtable: for each slot it lists the base implementation, how many subclasses override it, and the calls and strings in its body. Pass slot numbers to print the base and one override.

`NameSlots.java` applies `analysis/slot_names.tsv` across the whole family. It renames the base implementation and every override, plus the vtable struct fields, so calls read `this->vftable->Update(this, dt)`. It also applies `analysis/field_names.tsv` to every family class struct.

**Input actions** are decoded in [`input_actions.h`](input_actions.h), from `PadController::QueryButton`/`QueryAction`. Each player has six logical buttons, stored as per-player tables of raw pad indices that `SetControlScheme` (`0x095200`) fills:

| scheme | jump | button 2 | button 3 | button 4 | block | digivolve |
|---|---|---|---|---|---|---|
| 0 (when `0x2f5638 == 1`) | A | X | B | Y | LT | RT |
| 0 (otherwise) | Y | A | X | B | LT | RT |
| 1 | A | X | Y | B | LT | RT |

The actions `Character` asks for:

| id | action | input |
|---|---|---|
| 0x14 | crouch | stick down |
| 0x15 | block | LT held |
| 0x16 | block + button 2 | probably grab |
| 0x17 | digivolve | RT; gated by the "nodigivolve" check |
| 0x18 / 0x19 | move right / left | stick |
| 0x1a | down-jump | stick down + jump |
| 0x1b | jump | jump button, or stick up when that option is on |
| 0x1c | super jump | stick flick up, only with `superJump` |
| 0x1d | mash | wiggle out of stun or a grab |

Ids 0x00–0x12 are lower-level queries: buffered stick directions (relative to screen or facing), wiggle counters, and buffered or held button presses.
The jump, block and digivolve buttons are certain from how `Character` uses them. Buttons 2, 3 and 4 are named by table only: button 3 has tap/hold variants (likely the attack), and button 4 adds charge in animation state 0xf. Slot 29 is renamed `TryDownJump`, since it reads action 0x1a, not the plain jump.
Left unnamed: slots 4, 6, 9, 10, 17, 20, 21, 23–25, 28, 30 and 31 (attack, grab and hit handling). Their evidence is too thin so far.

**Why `Character` was missed:** 16 of its 36 vtable methods, and the whole `LoadMatch` function, were never defined as functions by Ghidra's analysis. Every scan therefore saw a 7-slot vtable and no constructor caller.
- `DefineMissingFunctions.java` now defines a function at every vtable entry that points to undefined code (328 functions), plus addresses passed as arguments.
- `ExtendVtables.java` then grows the vtable structs that became longer (14 classes) and moves the 112 new methods into their classes.

## What's known so far

- **Resource system:**
  - `Res_LoadFile`, `Res_ValidateHeader` (magic `res\n`, version 7.0, platform byte; the error text names the GameCube, so the engine was multi-platform).
  - `Res_Find(name, fourcc, prev)`, `Res_FindNextOfType`, `ResType_Find` / `ResType_Register`.
- **Lua:** `Lua_RunScriptResource` loads `lua!` resources through `luaL_loadbuffer` (Lua 5.0, in `lib/lua/`).

- **122 config readers** found through Lua key strings (see `analysis/lua_key_functions.tsv`), e.g. `FUN_000fe720`, which reads 82 attack/knockback keys.
- **Asset formats** are fully documented in the top-level README. They give the expected structure layouts for typing the loader code.
